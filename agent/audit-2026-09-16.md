# 具體程式缺陷稽核（2026-09-16）

使用者要求：「請你檢查具體的代碼看看有沒有bug類的」。本輪沿用 `question.md` 的驗收、技術棧與功能範圍；由主代理閱讀實作、重現問題、修復及複驗，沒有呼叫子代理。

## 已確認並修復

| 問題 | 觸發與影響 | 修復及測試 |
| --- | --- | --- |
| 預設 SQLite URL 未編碼目錄 | 資料目錄含 `#` 時啟動失敗；含 `%da` 等內容時會被解碼，資料庫可能建立到非預期目錄 | `runtime.go` 使用 `url.URL` 建立 URL；`TestDefaultDatabasePreservesSpecialDirectoryNames` 驗證精確位置及重開後資料 |
| SQLite DSN 將檔名字元當成選項 | Linux 合法檔名含 `?`，即使外部 URL 已編碼，轉換 DSN 時仍可能打開不同檔案 | `store.go` 使用編碼後的 `file:` URI；`TestSQLiteEscapedPathOpensExactFile` 驗證精確檔案與 WAL，另涵蓋 `%23`、`#`、空白 |
| 舊輪詢覆寫較新的管理結果 | 刪除主機後，較早發出的 GET 晚到，使主機重新出現在畫面；舊 GET 失敗也會顯示過時錯誤 | `App.vue` 為完整 refresh 加入遞增版本，過時成功／失敗皆忽略；兩個延遲回應案例驗證主機不再出現、沒有過時錯誤 |
| 更新中途失敗未還原 | 兩個安裝器已替換 binary，接著寫服務檔失敗時，`set -e` 直接結束，留下部分更新 | 將替換階段的失敗集中交給 EXIT trap，恢復原 binary／服務檔及使用者啟動器；注入寫入失敗 exit 73，驗證舊檔完整還原及原退出碼保留 |

## RED → GREEN 證據

1. SQLite：先新增測試，Windows 重現 `#` URL 拒絕與 `%` 路徑改變；WSL Linux 額外重現 `?` 檔名被切成 DSN query。修復後 Windows／Linux store 測試全部通過，Linux store race 通過。
2. 前端：先掛住舊 `/api/nodes`，完成刪除與新一輪讀取後，再回傳舊資料或 503。兩例分別因主機再次出現、錯誤提示污染而 RED；加入 refresh 版本後全 14 項 Vue 測試 GREEN。
3. 安裝器：先令服務檔寫入部分內容後 exit 73，兩例都因 binary 未恢復而 RED；修復後原檔與退出碼驗證 GREEN。另補首次安裝失敗後重試的兩項回歸，首跑即通過，不列為額外缺陷或 RED。

Linux 的 `?` 檔名案例僅在支援該檔名的平台加入，Windows 不建立非法檔名，也不產生略過案例。測試使用暫存資料庫、隔離 HOME 和模擬服務命令；沒有更動本機正式服務或既有資料。
